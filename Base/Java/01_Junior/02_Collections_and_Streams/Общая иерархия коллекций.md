# Общая иерархия коллекций в Java

> **Java Collections Framework** держится на двух несвязанных корнях: `Collection<E>` (группа отдельных элементов) и `Map<K,V>` (пары ключ-значение). `Map` **не** реализует `Collection` — у них несовместимые контракты добавления элементов (`add(E)` vs `put(K,V)`).
> На интервью: почему `Map` не extends `Collection`, чем `Queue` отличается от `List` по контракту, что даёт `SequencedCollection` (Java 21).

## Дерево наследования

```
Iterable<T>
  │
  └── Collection<E>                      ← группа элементов, "можно перебрать, добавить, удалить"
        │
        ├── List<E>                      ← упорядоченная, допускает дубликаты, доступ по индексу
        │     ├── ArrayList
        │     └── LinkedList  ───────────┐  (реализует и List, и Deque)
        │                                │
        ├── Set<E>                       │  ← уникальные элементы, equals()+hashCode()
        │     ├── HashSet                │
        │     ├── LinkedHashSet          │
        │     └── SortedSet<E>           │
        │           └── NavigableSet<E>  │
        │                 └── TreeSet    │
        │                                │
        └── Queue<E>  ────────────────────┘  ← элементы для обработки по порядку (FIFO/приоритет)
              ├── PriorityQueue
              └── Deque<E>                  ← двусторонняя очередь (стек + очередь)
                    ├── ArrayDeque
                    └── LinkedList

Map<K, V>                                ← отдельная иерархия, НЕ Collection
  ├── HashMap
  ├── LinkedHashMap
  ├── SortedMap<K,V>
  │     └── NavigableMap<K,V>
  │           └── TreeMap
  └── ConcurrentHashMap (+ другие java.util.concurrent реализации)
```

Пунктирная связь `LinkedList` — она одновременно `List` и `Deque`: единственный класс стандартной библиотеки, стоящий на пересечении двух ветвей. Практическая польза узкая: если нужен и индексный доступ (`List`), и O(1) вставка/удаление на краях (`Deque`) через одну и ту же ссылку — `LinkedList` даёт оба API без приведения типов. На практике это редкий кейс: если нужна в основном очередь/стек — берут `ArrayDeque` (быстрее из-за непрерывной памяти), если нужен в основном индексный доступ — `ArrayList`.

## Почему `Map` не extends `Collection`

Формальная причина — несовместимость контрактов на уровне сигнатур методов:

| | `Collection<E>` | `Map<K,V>` |
|---|---|---|
| Добавление | `boolean add(E e)` — один элемент | `V put(K key, V value)` — пара, возвращает старое значение |
| Хранит | Элементы `E` | Пары ключ→значение |
| Итерация | `Iterator<E>` напрямую (`for (E e : collection)`) | Не `Iterable` — итерируются только *представления*: `keySet()`, `values()`, `entrySet()` |
| Проверка наличия | `contains(Object o)` — есть ли элемент | `containsKey(K)` / `containsValue(V)` — раздельно для ключа и значения |

Если бы `Map` реализовывал `Collection<Entry<K,V>>`, метод `add(Entry<K,V>)` дублировал бы семантику `put()` с другой сигнатурой, а `contains()` был бы неоднозначен (по ключу? по значению? по паре?). Design Java Collections Framework (Joshua Bloch) сознательно разделил эти две модели данных.

**Мост между ними** — `Map` предоставляет три метода, возвращающих `Collection`-представления (views), через которые Map всё же можно перебирать привычным способом:

```java
Map<String, Integer> map = new HashMap<>(Map.of("a", 1, "b", 2));

Set<String> keys          = map.keySet();    // Set<K> — уникальные ключи
Collection<Integer> vals  = map.values();     // Collection<V> — значения, дубликаты возможны
Set<Map.Entry<String, Integer>> entries = map.entrySet(); // Set<Entry<K,V>> — пары

// Все три — VIEWS: изменения в map видны через них и наоборот
for (Map.Entry<String, Integer> e : entries) {
    System.out.println(e.getKey() + " = " + e.getValue());
}
```

Подробности `HashMap`/`TreeMap`/`ConcurrentHashMap` — см. [[Интерфейс Map]].

## `List` vs `Set` vs `Queue` — контракт, а не только реализация

- **`List<E>`** — порядок = позиция (индекс). Дубликаты разрешены. Основной вопрос "что на позиции i?". См. [[Интерфейс List]].
- **`Set<E>`** — порядок (если есть) вторичен, главное — уникальность через `equals()`/`hashCode()`. Основной вопрос "есть ли такой элемент?". См. [[Интерфейс Set]].
- **`Queue<E>`** — порядок = порядок обработки (FIFO у `LinkedList`/`ArrayDeque`, по приоритету у `PriorityQueue`). Основной вопрос "что следующее?". Ключевые методы — `offer()`/`poll()`/`peek()` (не бросают исключение при пустой очереди/переполнении, в отличие от `add()`/`remove()`/`element()`).
- **`Deque<E>`** (double-ended queue) — очередь с двух концов; может работать и как `Queue` (FIFO), и как стек (LIFO через `push()`/`pop()`). `ArrayDeque` — рекомендуемая замена и `Stack`, и `LinkedList` как очереди (см. подводные камни в [[Интерфейс List]]).

Все три — `Iterable` через `Collection`, поэтому `for-each` работает одинаково для `List`, `Set` и `Queue`; механику `Iterator`/`ConcurrentModificationException` — см. [[Интерфейсы Iterator и Iterable]].

## `SortedSet`/`NavigableSet` и `SortedMap`/`NavigableMap`

Обе параллельные иерархии (`Set`↔`Map`) имеют одинаковую надстройку для упорядоченных данных:

- `SortedXxx` — базовый контракт сортировки (`first()`, `last()`, `comparator()`).
- `NavigableXxx` (Java 6+) — расширяет `SortedXxx` методами позиционного поиска: `floor()`/`ceiling()`/`lower()`/`higher()`, `pollFirst()`/`pollLast()`, `descendingSet()`/`descendingMap()`.

`TreeSet` реализует `NavigableSet`, `TreeMap` — `NavigableMap`. Подробный API — в [[Интерфейс Set]] и [[Интерфейс Map]].
