# Java Generics

> Обобщённые типы переносят проверку типов с рантайма (`ClassCastException`) на компиляцию. На интервью чаще всего спрашивают: как работает Type Erasure и что от него остаётся в байт-коде (Signature Attribute), правило PECS (Producer-`extends`, Consumer-`super`), зачем нужны Bridge Methods, почему `list.set(0, list.get(0))` не компилируется для `List<?>`, и что такое Heap Pollution.

## Основы дженериков

**Зачем нужны (Java 5+):** до дженериков коллекции хранили `Object`, и каждый `get()` требовал ручной каст с риском `ClassCastException` в рантайме. Дженерики переносят проверку типов на этап компиляции — несовместимость типов ловится сразу, а не после падения в проде.

### Обобщённый класс/интерфейс

```java
class Box<T> {
    private T value;
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}

Box<String> box = new Box<>();
box.set("hello");
String s = box.get(); // без каста
```

- `T` — параметр типа (конвенция: `T` — Type, `E` — Element, `K`/`V` — Key/Value, `R` — Result).
- Параметров может быть несколько: `class Pair<K, V> { ... }`.

### Обобщённый метод

Параметр типа объявляется перед возвращаемым типом — метод может быть generic даже в обычном классе:

```java
static <T> T firstOrDefault(List<T> list, T def) {
    return list.isEmpty() ? def : list.get(0);
}

Integer x = firstOrDefault(List.of(1, 2, 3), 0);
```

### Bounded type parameters (ограничение типа)

```java
class NumberBox<T extends Number> {
    private T value;
    double asDouble() { return value.doubleValue(); } // доступны методы Number
}
```

- `T extends Number` — верхняя граница: `T` должен быть `Number` или его наследником (для интерфейсов тоже пишется `extends`, не `implements`).
- Без ограничения `T` эквивалентен `Object` — доступны только его методы.

### Wildcards — база

- `List<?>` — список неизвестного типа (unbounded wildcard). Читать можно только как `Object`, писать нельзя (кроме `null`).
- `List<? extends T>` / `List<? super T>` — ограниченные wildcard'ы, детальный разбор в PECS ниже.

### Raw Types — почему их избегают

```java
List list = new ArrayList();     // raw type — без параметра
list.add("string");
list.add(42);                    // компилируется, но логическая ошибка
String s = (String) list.get(1); // ClassCastException в рантайме
```

Raw types сохранены только ради обратной совместимости с до-generic кодом (Java 1.4-). В новом коде так писать нельзя — компилятор не просто так выдаёт unchecked-warning.

## Глубокое погружение в Type Erasure и байт-код

**Type Erasure** — это не просто удаление типов, это сложная трансформация кода для сохранения бинарной совместимости.

### Signature Attribute против Descriptors

Многие думают, что после компиляции информация о дженериках исчезает полностью. Это миф.

- **Descriptor** метода действительно содержит стертые типы (например, `Ljava/util/List;` вместо `List<String>`).
    
- **Signature Attribute** — это специальное поле в байт-коде, которое сохраняет информацию о дженериках для Reflection и компилятора. Именно благодаря ему IDE «понимает», что в `ArrayList<String>` нужно подставлять строки, когда вы подключаете скомпилированную библиотеку.
    

### Вставка Checkcast

Когда вы пишете `String s = list.get(0)`, в байт-коде это превращается в две операции: `invokevirtual` (вызов метода `get`, возвращающего `Object`) и `checkcast` (приведение к `String`). Если вы «обманули» компилятор через Raw Types, именно на `checkcast` вылетит `ClassCastException`.

Отсюда прямое следствие для перегрузки методов: в одном классе не могут сосуществовать `void m(List<String> l)` и `void m(List<Integer> l)`. После стирания их дескрипторы становятся идентичными — `void m(List l)` — и компилятор выдаёт ошибку компиляции «erasure of method is the same as another method»: на уровне JVM это один и тот же метод, различить перегрузки по метаданным дженериков во время вызова невозможно.

## PECS: Ковариантность и Контравариантность в деталях

Логика `? extends` и `? super` — это фундаментальный механизм обеспечения типобезопасности при наследовании коллекций.

### Ковариантность (`? extends T`)

**Математическое определение:** «Связь сохраняется». Если $A \subset B$, то $G<A> \subset G<? \text{ extends } B>$.

- **Практика чтения:** Мы уверены, что любой объект в списке является как минимум `T`. Поэтому чтение безопасно.
    
- **Запись:** Запрещена (кроме `null`). Мы не можем гарантировать, что добавляемый объект совместим с реальным типом списка в памяти (например, нельзя положить `Integer` в `List<? extends Number>`, так как там может быть `Double`).
    
- **Роль:** **Producer** (отдает данные).

### Контравариантность (`? super T`)

**Математическое определение:** «Связь оборачивается». Если $A \subset B$, то $G<B> \subset G<? \text{ super } A>$.

- **Запись:** Безопасно. Мы знаем, что список может принять `T`, так как он типизирован либо самим `T`, либо кем-то выше по иерархии (его предками).
    
- **Чтение:** Небезопасно. Мы не знаем, насколько «высоко» по иерархии ушел тип, поэтому можем извлечь только `Object`.
    
- **Роль:** **Consumer** (принимает данные).

Пример из стандартной библиотеки — `Collections.copy(List<? super T> dest, List<? extends T> src)`. `src` объявлен как Producer (`? extends T`), потому что метод только читает из него; `dest` — как Consumer (`? super T`), потому что метод только пишет в него. Разные wildcard'ы на двух параметрах одного метода — прямое применение PECS: это позволяет, например, копировать из `List<Integer>` в `List<Number>`, что было бы невозможно, потребуй метод точного совпадения типов у обоих параметров.

## Мостовые методы (Bridge Methods) и полиморфизм

Когда класс реализует интерфейс типа `Comparable<MyClass>`, возникает конфликт. Интерфейс после стирания требует `compareTo(Object)`, а ваш класс реализует `compareTo(MyClass)`. Сигнатуры не совпадают — полиморфизм ломается.

### Механика Bridge Method

Компилятор незаметно добавляет в ваш класс метод:

```java
// Генерируется компилятором (Synthetic)
public int compareTo(Object other) {
    return compareTo((MyClass) other); // Вызов вашего метода с кастом
}
```

Этот метод помечен флагами `ACC_BRIDGE` и `ACC_SYNTHETIC`.

Эти флаги важны при работе с Reflection: `Class.getDeclaredMethods()` возвращает **оба** метода — и ваш `compareTo(MyClass)`, и синтетический bridge `compareTo(Object)`. Код, который автоматически обрабатывает методы через Reflection (мапперы, сериализаторы, AOP-прокси), должен явно фильтровать bridge-методы через `method.isBridge()` — иначе одна и та же логическая операция может быть выполнена дважды: один раз для настоящего метода, второй раз для сгенерированной обёртки.

## Wildcard Capture: Почему `set(get())` не работает?

Рассмотрим код, который не компилируется:

```java
void foo(List<?> list) {
    list.set(0, list.get(0)); // Compile Error
}
```

**Почему так происходит:** При работе с `<?>` компилятор создает внутреннее имя типа, называемое **Capture** (например, `capture#1 of ?`). Для каждой операции захват происходит заново. Компилятор не может доказать, что `get()` вернул именно тот подтип, который ожидает `set()`, даже если это один и тот же список.

**Решение (Helper Pattern):**

```java
public void foo(List<?> list) {
    fooHelper(list);
}

private <T> void fooHelper(List<T> list) {
    list.set(0, list.get(0)); // Теперь T зафиксирован и операция разрешена
}
```

## Super Type Tokens: Обход Erasure в Runtime

Информация о `List<String>` стирается в полях и методах, но она остается в определении **класса**.

### Трюк Neal Gafter (Gafter's Gadget)

Если создать анонимный подкласс `new TypeReference<List<String>>() {}`, то информация о родительском типе сохраняется в метаданных этого подкласса.

```java
abstract class TypeReference<T> {
    private final Type type;
    protected TypeReference() {
        Type superclass = getClass().getGenericSuperclass();
        this.type = ((ParameterizedType) superclass).getActualTypeArguments()[0];
    }
}
```

Это база для работы Jackson, Gson и Hibernate при десериализации сложных коллекций.

У приёма есть runtime-цена: каждое выражение `new TypeReference<X>() {}` создаёт **новый анонимный класс** — не переиспользуемый объект, а именно новый класс со своими метаданными в Metaspace. Если создавать такие токены динамически в цикле или на каждый входящий запрос (вместо того чтобы держать их как статические константы), классы накапливаются в Metaspace, а выгружаются они JVM крайне неохотно (только вместе со своим classloader'ом) — это создаёт риск утечки памяти, специфичной именно для Metaspace, а не для обычного heap.

## Рекурсивные дженерики и Multiple Bounds

### Множественные ограничения

Синтаксис `<T extends Number & Comparable<T>>` позволяет накладывать несколько условий на тип.

- **Порядок важен:** Класс должен стоять первым, затем интерфейсы.
    
- **Стирание:** Тип `T` будет стерт до **первого** ограничения (в примере — до `Number`).
### Recursive Generics

Это паттерн, где тип расширяет дженерик от самого себя: `class MyClass<T extends MyClass<T>>`. Это часто используется в **Fluent API** (Builder), чтобы методы родительского класса возвращали тип наследника, не теряя цепочку вызовов.

## Heap Pollution и массивы дженериков

**Heap Pollution** — это рантайм-утечка неправильного типа в переменную.
### Почему `new T[10]` — это табу?

Массивы в Java **ковариантны** (`String[]` является подтипом `Object[]`) и проверяют типы в рантайме. Дженерики — **инвариантны** и стираются. Если разрешить `List<String>[]`, то через приведение к `Object[]` в этот массив можно было бы положить `List<Integer>`, что привело бы к «загрязнению» и взрыву приложения в самом неожиданном месте.

`@SafeVarargs` подавляет предупреждение компилятора об unchecked generic array creation для varargs-параметра (сам массив `T[]` под капотом varargs всё равно создаётся, несмотря на то что дженерики стёрты и такой массив в общем случае небезопасен). Аннотацию можно поставить только на `static`, `final`, `private` методы или конструкторы — то есть на методы, которые невозможно переопределить: если бы подкласс мог переопределить такой метод, он мог бы нарушить гарантию безопасности, которую даёт аннотация в родителе. Ответственность разработчика конкретна: не сохранять элементы varargs-массива в другой массив/поле и не возвращать наружу ссылку на сам этот массив — иначе обращение к нему извне (например, через Raw Type) может привести к `ClassCastException`, а компилятор об этом уже не предупредит.

## Подводные камни

- **Raw Types в новом коде** — обходят проверку типов компилятором, приводят к `ClassCastException` в рантайме на `checkcast`. Используй параметризованные типы или `<?>`, но не raw.
- **Overloading после Erasure** — методы, различающиеся только параметром типа дженерика, после стирания получают одинаковый Descriptor → compile error "erasure of method is the same as another method".
- **`? extends` не даёт писать** — попытка `list.add(x)` в `List<? extends T>` (кроме `add(null)`) — ошибка компиляции, компилятор не может гарантировать совместимость.
- **TypeReference в цикле/на каждый запрос** — каждый `new TypeReference<X>() {}` создаёт новый анонимный класс. Динамическая генерация в hot path — риск Metaspace leak, классы оттуда выгружаются неохотно.
- **Множественные bounds и стирание** — `<T extends Number & Comparable<T>>` стирается до **первого** типа (`Number`). Порядок в объявлении не косметический.
- **Bridge-методы и Reflection** — `getDeclaredMethods()` возвращает и синтетический bridge-метод, и «настоящий». Фильтруй через `method.isBridge()`, иначе логика фреймворка/маппера выполнится дважды.
