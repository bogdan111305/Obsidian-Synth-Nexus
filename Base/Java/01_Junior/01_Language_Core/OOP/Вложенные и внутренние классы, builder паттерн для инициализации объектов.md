Вложенные классы в Java — это способ сгруппировать логику, которая не имеет смысла в отрыве от основного класса. Однако за этим синтаксическим сахаром скрываются серьезные механизмы управления памятью и байткодные нюансы.

---
## Четыре всадника вложенности

В Java есть четыре способа объявить класс внутри другого класса. Выбор правильного типа — это вопрос производительности и чистоты архитектуры.

|**Тип**|**Модификатор**|**Ссылка на внешний (this$0)**|**Как создать**|
|---|---|---|---|
|**Static Nested**|`static`|**Нет**|`new Outer.Nested()`|
|**Inner Class**|—|**Да**|`outerObj.new Inner()`|
|**Local Class**|—|**Да**|Только внутри метода|
|**Anonymous**|—|**Да**|`new Interface() { ... }`|

---
## Static Nested Class: Просто сосед

Статический вложенный класс — это обычный класс, который просто «живет» внутри другого для удобства упаковки.

- **Связь:** Он не имеет доступа к нестатическим полям внешнего класса.
    
- **Зачем:** Группировка вспомогательных сущностей (например, `Builder` для основного класса или `Map.Entry` в `HashMap`).

---
## Inner Class: Скрытая угроза `this$0`

Нестатический вложенный класс (Inner) всегда хранит неявную ссылку на объект внешнего класса. В байткоде это поле называется **`this$0`** и является **синтетическим** (synthetic) — то есть сгенерировано компилятором и в исходном коде не прописано. Именно через `this$0` inner-класс получает доступ ко всем, включая `private`, полям и методам внешнего объекта (тот же механизм bridge-методов компилятора, что нарушает формальную инкапсуляцию, — см. [[Инкапсуляция]]).

Ссылка `this$0` — не опция, а обязательный параметр: компилятор инициализирует её в конструкторе inner-класса точно так же, как обычное поле, только неявно, и для этого ему нужен конкретный экземпляр внешнего класса ещё до вызова `new`. Именно поэтому инструкция создания inner-объекта выглядит как `outerObj.new Inner()` — синтаксис явно требует внешний экземпляр, а не просто ссылку на класс: без него `this$0` инициализировать нечем.

> **Senior Note (Memory Leak):** Если внутренний класс живет дольше внешнего (например, вы передали его как callback в другой поток), внешний объект не будет удален сборщиком мусора (GC), пока жив внутренний, — ведь `this$0` держит на него живую ссылку. Это классический источник утечек памяти в Android и GUI-приложениях.

## Local & Anonymous: Захват переменных

Эти классы определяются «на лету» внутри методов.

### Effectively Final

Вы замечали, что анонимный класс или лямбда не позволяют менять локальную переменную из метода?

```java
int count = 0;
Runnable r = () -> count++; // Ошибка компиляции!
```

**Почему?** Переменная копируется внутрь объекта класса. Если бы она менялась в методе, копия внутри объекта стала бы неактуальной. Чтобы избежать рассинхрона и проблем с многопоточностью, Java требует, чтобы такие переменные были `final` или `effectively final` (не менялись после инициализации).

Local class — это именованный класс, объявленный прямо внутри тела метода (в отличие от анонимного, у которого нет имени и который объявляется и создаётся одновременно через `new Interface() {...}`). Local class нужен, когда возможностей анонимного класса не хватает: его можно создать несколько раз в пределах метода, он может реализовать сразу несколько интерфейсов или иметь несколько методов и собственных конструкторов — анонимный класс ограничен одним расширяемым классом/интерфейсом и телом без явного конструктора. Как и анонимный, local class хранит `this$0` (если объявлен в нестатическом методе) и подчиняется тем же правилам захвата effectively final переменных.

### Anonymous vs Lambda

Лямбды (Java 8+) почти полностью вытеснили анонимные классы для функциональных интерфейсов (интерфейсов с единственным абстрактным методом). Разница не только в скорости: анонимный класс всегда компилируется в отдельный `.class`-файл (`Outer$1.class`) ещё на этапе сборки. Лямбда же не порождает отдельного класса на этапе компиляции вообще — вместо этого в байткод вставляется инструкция `invokedynamic`, которая при первом вызове обращается к `LambdaMetafactory` и лениво генерирует реализующий класс прямо в рантайме (и переиспользует его при последующих вызовах). Это и быстрее, и не засоряет classpath десятками файлов вида `Outer$1.class`, `Outer$2.class`.

## Паттерн Builder: Прощай, Телескоп

Когда у класса больше 5-6 параметров, конструкторы превращаются в «телескопы» (один вызывает другой с дефолтным значением). Это неудобно и легко ошибиться в порядке `boolean` флагов.

**Решение — Builder:**

- Использует **Static Nested Class** — Builder-у не нужен доступ к состоянию несуществующего пока основного объекта, поэтому связь с внешним классом (`this$0`) здесь не только не нужна, но и была бы лишним поводом для утечки памяти.
    
- Позволяет собирать объект пошагово: каждый метод-сеттер возвращает `this` (см. Fluent API в [[Поля, конструкторы, this, инициализаторы]]), что даёт цепочку вызовов вместо одного перегруженного конструктора с десятком параметров.
    
- Гарантирует иммутабельность (поля в основном классе — `final`): промежуточное, потенциально невалидное состояние существует только внутри объекта `Builder`, а сам основной класс собирается одним финальным вызовом `build()`, минуя стадию частично заполненного объекта.

```java
// Fluent API в действии:
Pizza pizza = new Pizza.Builder("Large")
    .cheese(true)
    .pepperoni(true)
    .build();
```

## Подводные камни (Pitfalls)

- **Serialization:** Внутренние (non-static) классы очень плохо сериализуются из-за ссылки на внешний класс. Если планируете передавать объект по сети — делайте вложенный класс `static`.
    
- **Shadowing:** Если во внутреннем и внешнем классах есть поля с одинаковым именем, используйте `Outer.this.fieldName` для доступа к полю внешнего класса.
    
- **Builder Validation:** Всегда делайте валидацию данных в методе `build()`. Это ваш последний рубеж перед созданием потенциально некорректного объекта.
