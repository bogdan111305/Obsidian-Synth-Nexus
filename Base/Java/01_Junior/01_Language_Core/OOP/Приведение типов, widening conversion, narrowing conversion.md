## Примитивные типы: Расширение и Сужение

В Java существует четкая иерархия «вместимости» типов.

### Widening (Расширение)

Происходит **автоматически**. Java уверена, что новое «ведро» больше старого, и данные не выльются.

`byte → short → int → long → float → double`

`char → int`

> **Ловушка интервью:** Является ли переход `int → float` расширением?
> 
> **Да**, это widening. Но это единственный случай расширения, где **возможна потеря точности**. У `int` — 32 бита для значения, а у `float` — только 23 бита для мантиссы. Числа больше $2^{24}$ (около 16.7 млн) будут округлены. Классификация «widening» здесь идёт не по точности хранения значения, а по спецификации Java: у `float` шире диапазон (за счёт экспоненты он покрывает числа, недостижимые для `int`), поэтому JLS считает такое преобразование расширением диапазона, даже если конкретное большое значение округляется.

### Narrowing (Сужение)

Требует **явного указания типа** (cast). Вы берете на себя ответственность за возможную потерю данных.

`double → float → long → int → short → byte`

- **Потеря точности:** При `(int) 3.9` дробная часть просто отсекается (результат `3`).
    
- **Переполнение:** При `(byte) 300` Java просто отрезает лишние биты. 300 в бинарном виде — `1 0010 1100`. Младшие 8 бит — `0010 1100`, что равно `44`.

- **Специальные значения `float`/`double`:** У них нет прямых аналогов в целых типах, поэтому JLS определяет для них фиксированные результаты сужения: `(int) Double.NaN` даёт `0`, `(int) Double.POSITIVE_INFINITY` — `Integer.MAX_VALUE`, а `(int) Double.NEGATIVE_INFINITY` — `Integer.MIN_VALUE`. Это не «мусорные» значения — они детерминированы и одинаковы на любой платформе.

## Ссылочные типы: Upcasting и Downcasting

Здесь правила диктует иерархия классов (наследование).

### Upcasting (Вверх по дереву)

Приведение подкласса к суперклассу. Всегда **безопасно**, происходит автоматически.

```java
Dog dog = new Dog();
Animal animal = dog; // Мы знаем, что любая собака — это животное
```

### Downcasting (Вниз по дереву)

Приведение суперкласса к конкретному подклассу. Нужен, когда переменная (поле, параметр, элемент коллекции) типизирована как более общий супертип, но в конкретной точке кода вам нужны методы или поля, объявленные только в подклассе и отсутствующие в контракте супертипа. **Опасно**, потому что компилятор не может проверить его на этапе компиляции — он лишь доверяет вашему касту, а реальную проверку типа объекта в памяти откладывает на рантайм.

```java
Animal a = new Dog();
Dog d = (Dog) a; // OK
Cat c = (Cat) a; // Runtime ошибка: ClassCastException
```

### Современный подход: Pattern Matching (Java 16+)

Забудьте про старый стиль с двойной проверкой. Используйте сопоставление с образцом:

```java
if (animal instanceof Dog d) {
    d.bark(); // 'd' уже приведена к Dog внутри блока
}
```

## Байткод

На уровне JVM операции приведения имеют свои команды:

- **Примитивы:** - 
	- **`i2l`**, **`i2f`**, **`i2d`**: Расширение (int в long, float, double).
	- **`l2i`**, **`f2i`**, **`d2i`**: Сужение (требует явного каста, может вызвать потерю данных).

- **Объекты:** Команда `checkcast`. Она проверяет дерево наследования в Runtime. Если типы несовместимы — выбрасывается `ClassCastException`.

## Числовые ловушки и Autoboxing

### Ошибка Boxing + Widening

Java умеет делать либо **boxing**, либо **widening**, но не оба сразу автоматически.

```java
Integer x = 10;
// Long y = x;       // ОШИБКА: нельзя превратить Integer в Long напрямую
Long y = (long) x;   // OK: сначала unboxing в int, потом widening в long, потом boxing
```

### Integer Cache

Это классика интервью. Java кэширует объекты `Integer` в диапазоне от **-128 до 127**. Это Flyweight-оптимизация: значения в этом диапазоне используются настолько часто, что JLS обязывает `Integer.valueOf(...)` (а автобоксинг всегда идёт именно через него, а не через `new Integer(...)`) переиспользовать заранее созданные объекты вместо аллокации новых. Верхнюю границу кэша можно расширить флагом `-XX:AutoBoxCacheMax`, но полагаться на это в бизнес-логике нельзя — контракт гарантирует только `[-128, 127]`.

```java
Integer a = 127, b = 127;
System.out.println(a == b); // true (ссылаются на один объект в кэше)

Integer c = 200, d = 200;
System.out.println(c == d); // false (созданы два разных объекта в куче)
```

**Правило:** Ссылочные типы всегда сравниваем через `.equals()`.

## `short` vs `char`: 16-битный тупик

Казалось бы, оба типа занимают 16 бит. Почему же они не приводятся друг к другу автоматически?

- **`short`**: Знаковый тип (от $-32\,768$ до $32\,767$).
    
- **`char`**: Беззнаковый тип (от $0$ до $65\,535$).

Поскольку `short` может хранить отрицательные числа, которые не влезут в `char`, а `char` может хранить значения больше $32\,767$, которые не влезут в `short`, Java требует **явного приведения** в обе стороны.

```java
short s = -10;
// char c = s;         // ОШИБКА: Compile-time error
char c = (char) s;     // OK: но результат будет 65526 (из-за особенностей дополнения до двух)

char c2 = 'A';
// short s2 = c2;      // ОШИБКА
short s2 = (short) c2; // OK
```

## Подводные камни (Pitfalls)

1. **Unboxing + null:**
    
```java
Integer i = null;
int x = i; // Привет, NullPointerException!
```
    
2. **Порядок в выражениях:**
    
```java
byte a = 10, b = 20;
// byte c = a + b; // ОШИБКА: арифметика в Java всегда идет в int. Результат будет int.
byte c = (byte) (a + b); // Правильно
```
    
3. **Narrowing в циклах:** Будьте осторожны при касте внутри циклов, это может привести к бесконечному циклу, если значение «прокрутится» через переполнение.
